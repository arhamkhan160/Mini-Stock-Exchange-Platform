The domain in 30 seconds

An exchange is a matchmaker

It sets no prices and owns nothing. It keeps a list of who wants to buy and who wants to sell, and pairs them when the prices meet.

Sellers above, buyers below. The best bid is always under the best ask — if they ever crossed, they would already have traded.

Rule 1 — price, then time

The cheapest seller is matched first. Ties are broken by who arrived first, which is why each price level is a queue.

Rule 2 — price improvement

Bid 200.00, cheapest ask is 195.70 → you pay 195.70. You named your worst acceptable price and got a better one.

So $2,000 was reserved but only $1,957 spent — the difference must be returned.

Rule 3 — you cannot sell what you do not own

Buys reserve cash; sells reserve shares. Without the second, a user could sell the same 10 shares twice.

Architecture

Split by what scales together

Four genuinely different engineering problems: market data is read-heavy, matching is latency-critical, cash is consistency-critical, notifications are fire-and-forget. One process would force one set of trade-offs on all four.

Database per service

Seven separate Postgres servers, not seven schemas. No service can read another's tables — it must ask over HTTP or learn from an event.

Cost: no foreign keys, no cross-service transactions. That is exactly why we need a saga.

sync when you need an answer now

Only two calls: Order → Account to reserve cash, Order → Portfolio to reserve shares. You cannot accept an order and then discover the user is broke.

async when something has happened

One trade.executed event updates five services. Five blocking calls would let the slowest one throttle the matching engine.

Placing an order

A saga, because there is no ROLLBACK

The flow spans three services and three databases. A distributed transaction is not available, so each step carries a compensating action that undoes it.

  1. Gateway validates the JWT and the rate limit (30 orders/min)
  2. Order validates symbol, quantity, and the $0.01 tick — bad input dies here, nothing persisted
  3. Order row written as PENDING, so the reservation has an ID to be idempotent against
  4. Account takes a Redis lock, checks buying power, reserves the cash — insufficient funds returns 409
  5. Status NEW, publish order.accepted — the pivot: no rollback past here
  6. Matching Engine pairs it by price–time priority and publishes trade.executed per fill

Then five services react, in parallel

Order marks it filled · Account settles both sides · Portfolio updates holdings and P&L · Market Data writes the candle and broadcasts a tick · Notification alerts both traders.

Compensation

Cash reserved, then the broker is down so the publish fails. Without compensation the money stays locked forever for an order that will never exist.

Release is idempotent and returns "released 0" rather than 404, so the orchestrator can compensate blindly without knowing how far it got.

Cancelling is two-phase

Only the book knows whether an order is still resting, so the engine publishes the authoritative order.cancelled. That is why the UI says "Cancelling…" — it can still come back filled.

When things fail

Four patterns, four failure modes

Not a checklist — each one answers a different question, and we measured the problem before choosing the fix.

The incident we measured

40 concurrent requests to a service that was down made a healthy service unreachable for 40 seconds.

DNS lookups share a thread pool. A lookup for a host that does not exist holds its thread far longer than the connect timeout — enough of them and nothing is left for the services that are up. A cascading failure.

40s → 14s after the fix

Circuit breaker — service is down

Stop calling it for 10s: no socket, no DNS lookup, no thread. Hard failures (no such host) open after 1; soft ones (timeout) need 4, so a blip cannot lock out a healthy service.

Bulkhead — stop it spreading

Cap in-flight requests per upstream at 8. One sick service can flood its own compartment, never the ship.

Retry + dead letter

A failed message waits in <queue>.retry for 5s, then returns. RabbitMQ does the waiting, so no consumer blocks. Dead-lettered after 5 attempts.

Idempotency

At-least-once delivery means every handler eventually sees a duplicate. The processed_events primary key is written in the same transaction as the work; Redis is a cache set after the commit.

Fail closed vs fail open

Redis down + reserving funds → refuse, or a user spends the same cash twice. Redis down + rate limiting → allow; protection is not correctness.

The bug worth telling you about

First run with real volume: zero trades. You can only sell shares you own, and only own them by buying — on a new exchange nobody can start. The logs were correct; the market was deadlocked. Real venues solve it with issuance, so we model it too.
